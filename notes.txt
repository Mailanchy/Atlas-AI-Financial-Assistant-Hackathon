Here is a quick cheat sheet summarizing exactly how your bot handles multiple users and why your database is set up this way. This is a great reference to have if the hackathon judges ask about your backend architecture!

### **1. How `telebot` Handles Concurrency (No Async Needed)**

* **Automatic Threading:** Instead of using `async/await`, the `telebot` library uses multi-threading in the background.
* **One Thread per Message:** Every time a user sends a message, `telebot` spawns a brand new, temporary thread (a mini-process) just to handle that specific message.
* **Simultaneous Users:** Because of these threads, your bot can process messages from 10 different users at the exact same time without the code getting "blocked" or making anyone wait in line.

### **2. The Advantage of Opening Database Connections Inside Functions**

* **Thread Safety:** SQLite is strict. If you create a database connection in your main setup code, it belongs to the "main thread." If a `telebot` worker thread tries to use that main connection, Python panics and throws a `ProgrammingError`.
* **Private Access:** By putting `sqlite3.connect()` *inside* your function, you guarantee that every single `telebot` thread builds its own private, safe connection to the database.
* **Prevents Lockups:** It stops the dreaded `database is locked` error. If two users message you at the exact same millisecond, they aren't fighting over the same database door.
* **Clean Clean-Up:** By connecting, executing, and closing (`conn.close()`) all in one block, you ensure you never leave dangling connections open that could slow down your server over time.

1. The Security Guard: PRAGMA foreign_keys = ON;By default, SQLite is extremely laid back. Even if you explicitly tell it that
 the preferences table is linked to the users table, SQLite actually ignores that rule by default (for backward compatibility 
 with really old software).  When you run PRAGMA foreign_keys = ON;, you are strictly enforcing the rules.  
 Why it matters: Remember how we added ON DELETE CASCADE to your tables? If a user asks to delete their account, 
 you only have to delete their ID from the main users table. Because you turned this PRAGMA rule on, SQLite will act like a 
 smart security guard and automatically run through all the other tables (history, memory, documents) and instantly 
 shred all of their linked data for you.

the database doesn't look at the messy pile at all. It looks at the beautifully sorted cheat sheet, instantly sees that 
User A's messages are at Row 1 and Row 3, and reaches right in to grab them.

Think of the @bot.message_handler as a Bouncer at a VIP club or a highly efficient Mail Sorter.

Whenever someone sends a message to your bot, Telegram throws that message at your Python script. 
The message_handler stands right on top of your function and looks at the incoming message. 
It asks: "Does this message match my specific rules?"

If YES, it lets the message pass through and triggers the function below it.

If NO, it ignores the message and lets it fall down to the next handler.

1. The Content (What did they send?)
This is the actual stuff the user wants you to see or hear.

message.text — The actual words typed by the user (will be empty if they sent a photo/voice).

message.content_type — A text tag telling you what kind of message it is (e.g., 'text', 'photo', 'voice').

message.photo — A list containing the image data in different sizes (if they sent a picture).

message.voice — The file data and duration of the audio clip (if they sent a voice note).

2. The Sender (Who sent it?)
Telegram tells you exactly who is talking to the bot.

message.from_user.first_name — The user's first name (e.g., "Husaima").

message.from_user.last_name — The user's last name (if they have one set).

message.from_user.username — Their public @handle.

message.from_user.id — A unique, permanent string of numbers tied to their specific Telegram account. This is how bots remember who you are.

3. The Chat (Where did it happen?)
This tells you where the conversation is taking place.

message.chat.id — The unique ID of the conversation. This is the most important piece of data if you ever want to send a message without using bot.reply_to. You need this ID to tell Telegram exactly which chat window to push your text into.

message.chat.type — Tells you if this is a private one-on-one chat ('private'), or if the bot was added to a group chat ('group' or 'supergroup').

4. The Metadata (The extra details)
message.message_id — A unique number for this exact message. You use this if you want your bot to delete or edit a specific message later.

message.date — The exact date and time the message was sent (stored as a Unix timestamp).
